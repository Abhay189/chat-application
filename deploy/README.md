# Production operations

Serve `frontend/dist` and the API from one HTTPS origin. The frontend production build uses `/api` by default. Use a managed PostgreSQL database or a protected local PostgreSQL installation, persistent storage, and automated backups.

1. Install pinned backend dependencies and `npm ci` frontend dependencies, then run `npm run build` in `frontend`.
2. Supply `APP_ENV=production`, a random `JWT_SECRET_KEY` of at least 32 characters, database credentials, and `CORS_ORIGINS=https://your-real-domain`. Set `TRUST_LOCAL_PROXY=1` only when the local proxy overwrites forwarded headers as shown in the nginx example. Keep the secret outside source control. Use a least-privilege runtime database role after migrations; use a separate migration role for schema changes.
3. Back up the database, then run `python -m flask --app backend/app.py migrate` from the repository root using the migration role. Migrations are versioned and transactional. A failed upgrade does not partially apply its schema changes. Take a snapshot before upgrading, and use a tested backup restore procedure for rollback.
4. Run `python backend/serve.py` under a service manager with automatic restart and log capture. Waitress binds to loopback port 5000. Keep that port and PostgreSQL port 5432 private. Do not use Flask's development server or Vite's development/preview servers as public production servers. [Flask deployment guidance](https://flask.palletsprojects.com/en/stable/deploying/).
5. Adapt `nginx.conf.example` with your actual domain, built frontend directory, and TLS certificate paths. Validate with `nginx -t`, then start/reload nginx. The example strips `/api/` before forwarding to Flask. Configure DNS and obtain a valid TLS certificate through your hosting provider/ACME. Never set production cookies to insecure to work around missing HTTPS.
6. Check `/api/health/ready`, register two synthetic accounts, add a contact, exchange/edit/delete a message, upload/download a file, edit a profile, refresh, log out, and verify session revocation over the actual HTTPS domain. Load-test anticipated concurrency and alert on elevated latency, 5xx responses, disk/database growth, and failed backups before opening registration publicly.
7. Run `python -m flask --app backend/app.py cleanup` daily with the application environment. It deletes expired session records, obsolete rate counters, and unreferenced attachments older than a day. Never delete active sessions to save space. Message/file retention and account deletion policy are product decisions and must be defined before public deployment.

Authentication uses HttpOnly, Secure production cookies and double-submit CSRF protection; active sessions are stored in PostgreSQL and logout revokes them. [JWT persistence guidance](https://flask-jwt-extended.readthedocs.io/en/stable/blocklist_and_token_revoking.html). There are no tokens in localStorage. The local theme cache contains a display preference only; database settings are authoritative after login.

Per-IP hourly limits currently cover registrations (20), login attempts (60), user searches (600), messages (1200), and uploads (100). They use shared database counters. The trusted proxy configuration is necessary for actual client IPs behind nginx. These limits are a basic abuse control, not a replacement for edge rate limiting or monitoring. The direct message and attachment authorization checks apply independently to every request.

Use TLS for remote database connections (`DATABASE_URL` supports `?sslmode=verify-full` with the appropriate CA). Enable provider encryption at rest and encrypted off-machine backups. Database backups contain private chats and file contents; restrict access and test restore procedures. This application does not offer end-to-end encryption.

Run dependency audits before releases (`npm audit --omit=dev` and `pip-audit` in a development environment), review changes to the lockfile, and apply patched versions. The last local production dependency scans reported no known vulnerabilities; this is point-in-time evidence, not a guarantee of security.

The local implementation has been tested, but hosting, DNS, TLS, backup/restore, production mail delivery, monitoring, and load testing require a chosen deployment environment. Email ownership verification and forgotten-password delivery are not available in this release. Browser alerts need the tab to remain open; no background push service is installed.
